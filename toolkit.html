Architecture patterns

Patterns chosen for the workload

No single architecture fits every pipeline. These are the patterns I use and the situations they help address.

Medallion architecture

Progressively improves raw data into validated and business-ready models with clear quality boundaries.

Sources → ADF and ADLS Gen2 → Databricks and PySpark → Bronze, Silver, Gold → Power BI

Lambda architecture

Combines reliable batch processing with a faster path when consumers need lower-latency updates.

Batch: ADF and Databricks
Speed: Spark Structured Streaming
Serve: SQL and BI models

Kappa architecture

Treats replayable event streams as the main source so one processing path can support continuous workloads.

Events and logs → Structured Streaming → append-only Delta tables → Spark SQL and Power BI

One big table

Produces a wide, consumption-ready table when repeated joins would make a focused analytics workload slower or harder to use.

Delta Lake and Spark SQL → governed joins → wide serving model → Power BI, Tableau, or Excel

Engineering practice

The tools support the operating model

See selected work View certifications

Performance

Partition strategy, adaptive query execution, clustering, autoscaling, and Photon are applied where measurements justify them.

Reliability

Schema controls, idempotent jobs, checkpoints, observable failures, and clear retry behavior reduce operational surprises.

Governance

Unity Catalog, access boundaries, lineage, and documented ownership keep data useful without weakening control.

Cost

Compute size, job duration, storage layout, and DBU use are treated as engineering constraints, not billing afterthoughts.
